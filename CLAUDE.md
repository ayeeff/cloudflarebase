# Cloudflarebase

Firebase alternative built natively on Cloudflare (Workers, Durable Objects, D1, KV, R2, Workers AI, Agents SDK). Agent-first: each backend primitive is a Cloudflare Agent, one Durable Object instance per client project.

Also read [AGENTS.md](AGENTS.md). Cloudflare APIs change frequently; retrieve current official documentation before Workers, Durable Objects, Agents, bindings, or limits work.

## Repository layout

Separate npm projects with separate Wrangler configs and generated `Env` types. Never import runtime code or generated Worker types across them. Shared DTOs are deliberately copied and must be kept in sync.

| Path             | Worker                                                                                                                                               | Purpose                                                                                                                                                                                                                                                       |
| ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`              | `cloudflarebase` (`cloudflarebase-com` in `env.production`)                                                                                          | SvelteKit 2/Svelte 5 dashboard and marketing site, shadcn-svelte, Tailwind v4, Cloudflare adapter                                                                                                                                                             |
| `agents/auth`    | `auth-agent` (`-local`, `-test`, or `-preview` by environment)                                                                                       | `AuthAgent` Durable Object, one per project; Better Auth and Drizzle over embedded DO SQLite                                                                                                                                                                  |
| `agents/db`      | `db-agent` (`-local`, `-test`, or `-preview` by environment)                                                                                         | `DbAgent` (coordinator, one per project) + `DbCollection` (one per collection) + `DbTable` (one per SQL table) + `DbGateway` (one-socket realtime, per region): documents and typed-column tables, both with live queries                                     |
| `agents/hosting` | `hosting-agent` (`-local`, `-test`, or `-preview`), plus `hosting-outbound` (`-preview` per environment; own tiny worker, `wrangler.outbound.jsonc`) | `HostingAgent` Durable Object, one per project: apps and functions on Workers for Platforms - deploy orchestration in the DO, `*.cfbase.dev` wildcard serving in the same worker (docs/managed-service-design.md Phase B)                                     |
| `agents/storage` | `storage-agent` (`-local`, `-test`, or `-preview` by environment)                                                                                    | `StorageAgent` (bucket registry + access config, one per project) + `StorageBucket` (object index, one per bucket): object storage on one shared R2 bucket, key-prefixed `p/<pid>/<bucket>/`, bytes streamed by the WORKER (docs/storage-agent-plan.md, S1)   |
| `cli`            | none (Node on the consumer's machine)                                                                                                                | `@cloudflarebase/cli`, the `cloudflarebase` bin: `init [name]` (bare = managed setup) / `add <agent>` / `deploy` / `secret put` / `key create\|list\|revoke` (service keys) / `login` / `logout` / `schema generate\|apply\|drop` (docs/schema-cli-design.md) |

The root Worker binds `AUTH_AGENT` + `DB_AGENT` + `HOSTING_AGENT` + `STORAGE_AGENT` (agent services) and `DB` (control-plane D1). Agent instances live at `/agents/<worker>/<projectId>/...`.

**Every agent ships a `cloudflarebase.agent.json` manifest** (`docs/agent-contract.md`, implemented). The app imports those files directly from `agents/<name>/` into `src/lib/agent-registry.ts` - single-sourced on purpose, so the console guard can never drift from what the package declares - and the guard route table, `/agents/*` dispatch, `/api/projects/<id>/<prefix>/*` proxy classification, sidebar navigation, project-delete fan-out, and per-agent OpenAPI modules (`src/lib/openapi/<name>.ts`) are all registry-driven. The CLI reads the manifest from the installed package and derives the entrypoint export lines from it.

**The top level of both Wrangler configs is the self-hosted default, not this project's deployment.** It publishes to workers.dev, claims no custom domain, and leaves `DEMO_MODE` unset so a fresh install is private. cloudflarebase.com lives in `env.production`, deployed with `npm run deploy:production`. The agent's `env.production` name is pinned to `auth-agent` (what the service binding resolves). The web `env.preview` is the **same Worker** as production (`cloudflarebase-com`): previews are versions of it, uploaded by Workers Builds from non-production branches, and the environment exists for its bindings - `AUTH_AGENT` targets `auth-agent-preview` - which versions carry individually.

## Architecture decisions

- **`agents/auth` is published as `@cloudflarebase/auth`.** Supabase's distribution model: the agent is a versioned artifact you depend on, not source you fork. A consumer owns their `wrangler.jsonc` and entrypoint. `files` ships `dist`, `template`, and `NOTICE` only. Mechanism and constraints in `agents/auth/CLAUDE.md`.
- **CI secrets live in GitHub environments, never repository secrets.** The agent deploy workflows declare `environment: production` / `environment: preview` (Cloudflare credentials, branch-restricted to `main` / `preview`), and publishing declares `environment: release`. **Every agent needs FOUR workflow touchpoints, and storage shipped with none of them until 2026-08-17** (deploy-prod, deploy-preview, the `release.yaml` package list + tag trigger, and a `quality.yaml` typecheck + unit-test pair): the agent contract covers the code, nothing enforced the CI, so a whole primitive was live in the repo, absent from npm, and deployed only by hand. Adding a primitive means adding all four - hosting's unit tests were missing from quality for the same reason and landed with them. Quality and e2e run untrusted PR code, so they hold no secrets and `permissions: contents: read`. The d1-migrate workflows were deleted: the control plane applies its schema at runtime, and they referenced a `migrations/` directory and `D1` binding that no longer exist.
- **Releases are merge-driven** (`.github/workflows/release.yaml`). Every push to `main` publishes each package whose `package.json` version is absent from the npm registry - bump on `preview`, merge, done. The registry is the ledger, so runs are idempotent (unchanged versions publish nothing, failed publishes self-heal on the next push, a never-published package ships on its first merge), and the ungated detect job means no-bump merges never ping the release reviewers. Tags (`auth-v*`, `db-v*`, `storage-v*`, `hosting-v*`, `cli-v*`) remain the manual escape hatch and refuse a tag/package.json mismatch. Every publish runs the full typecheck (which is what executes `bindings.test-d.ts`; the build config excludes it). Publishing is npm trusted publishing (OIDC): no token exists anywhere, npmjs.com accepts only this repo + workflow + `release` environment, whose required reviewers gate every publish. Provenance requires a public repo.
- **The CLI is the delivery mechanism.** `add <agent>` npm-installs the agent, merges its `template/wrangler-fragment.jsonc` (jsonc-parser; comments survive, user values never overwritten, collections merge by binding name, DO migrations append under the next free tag), prepends the entrypoint re-export with the `AssertAuthAgentEnv` check, and reruns `wrangler types`. Every step idempotent. Fragments and templates ship inside each agent's package, so a new primitive is one registry entry in `cli/src/lib/agents.ts`. Agents are DO classes in the consumer's single Worker; `add` never means another deploy. `deploy` deploys once and reports the URL (the agent trusts its own origin, so nothing needs configuring first). Managed `deploy` resolves its credential most-explicit-first: `--token`/`CLOUDFLAREBASE_DEPLOY_TOKEN`, then GitHub's Actions OIDC identity token (`cli/src/lib/oidc.ts` - minted by the CLI, not the workflow, so the generated YAML stays checkout/build/deploy; audience is the console origin, and a missing `ACTIONS_ID_TOKEN_REQUEST_URL` inside Actions throws naming the real cause, a missing `id-token: write`), then the stored login. Config likewise falls back from `cloudflarebase.json` to `CLOUDFLAREBASE_PROJECT`/`_APP`/`_URL` (all three or none) - the file always wins, so a linked directory is never redirected by an ambient variable. `CLOUDFLAREBASE_<AGENT>_SPEC` overrides the install source.
- Drizzle is the database layer (`drizzle-orm/durable-sqlite`); drizzle-kit output is inlined into `src/migrations.ts` as string literals and applied in `onStart`. Inlining instead of `.sql` text modules is what lets the agent ship as a plain npm dependency. Better Auth runs inside each `AuthAgent` with the Drizzle SQLite adapter, `transaction: false`, and project-scoped cookie prefixes.
- Simple RBAC: `user.role` (default `user`) is a Better Auth additional field with `input: false`; the dashboard's `PUT /admin/users/:id/role` proxy is the only writer. Roles are a per-project registry of `{ name, permissions[] }` (`PUT /admin/roles`, agent state, built-in `user`/`admin` always present). The `jwt` plugin issues project-signed JWTs on `GET /token` (keys on `GET /jwks`, keypair in the agent's `jwks` table) with `email`, `role`, and `permissions` claims. **On the console instance only, the agent refuses self-inflicted lockout** (2026-08-15): 409 on an admin demoting themselves (whatever the admin count), and 409 on demoting or deleting the LAST admin - the first account additionally becomes admin at creation (`onUserCreated` → `ensureConsoleAdmin`), not on its first console request. Customer projects keep unrestricted role churn: their roles are application RBAC and cannot strand anyone. Pinned by `e2e/console-guard.api.spec.ts`.
- The browser uses same-origin `/api/projects/<id>/...` SvelteKit endpoints, proxied over `AUTH_AGENT` preserving cookies, origin, and the edge-resolved country header.
- **Console auth.** Every operator surface requires a session, enforced by `consoleGuardHandle` in `src/hooks.server.ts` across `/dashboard/*`, `/api/*`, and the `/agents/*` passthrough (which reaches the DO without a proxy). Sessions resolve from cookies OR a bearer `Authorization` header (the CLI's path); since Phase A the guard resolves the full IDENTITY - session + org memberships + pending invitations - in ONE agent round trip (`getConsoleIdentity` → the agent's `GET /console/me`; 404 falls back to plain get-session with no orgs so a pre-Phase-A agent degrades instead of signing everyone out), memoized as `locals.consoleIdentity` beside `locals.consoleUser`. **The lookup has THREE answers, not two** (`resolveConsoleIdentity`): signed in, anonymous, and `unavailable` - the agent never got to check. Collapsing the third into "anonymous" is what made operators randomly signed out and then stuck: the guard bounced to `/login?next=`, and that page resolves the session the same way and fails the same way, so signing in again could not break the loop. `unavailable` now answers 503 (`cannotVerifySession`) on both pages and APIs, because the operator's credentials are not the problem. The cause was rate limiting: a service-binding fetch carries NO Cloudflare headers, so the agent saw no client IP and bucketed every operator's session read into one shared 100/60s counter, which a 5s-polling console exhausts in under a minute - the guard now forwards `cf-connecting-ip` and the agent gives `/get-session` its own generous rule. Console sessions last **30 days** idle (sliding, extended once per day of use). **Reserved ids are not projects** (2026-08-13): the guard refuses every one of them before resolving a session, EXCEPT `console` itself, which is real (it holds every operator account) and is gated on the console `admin` role - never on ownership, which cannot speak for a non-registry row. `CONSOLE_DASHBOARD_PAGES` keeps the static `/dashboard/organization` route from being classified as a project. This was a live privilege escalation until 2026-08-13: the ownership check SKIPPED reserved ids, so any registered account reached `/dashboard/console` and the admin proxies behind it - listing, deleting, and re-roling every operator on the deployment. `ensureConsoleAdmin` in the agent heals the administrator into place (the earliest non-guest account, only while no admin exists, so it is a one-time repair and a standing one for a console whose last admin left), and `/console/me` reads the role from the TABLE rather than the session payload so the 60s cookie cache cannot keep a demotion unenforced. The CLI login hand-off is `/cli-auth` (operator page; approve form-POSTs the token from `POST /api/cli/token` to the CLI's localhost listener) - pinned by `e2e/cli-auth.{api,ui}.spec.ts`. Public by exception only: `/api/projects/<id>/auth/*`, `/config`, `/openapi.json`, `/api/github/webhook`, and `/api/github/callback` (the last two authenticate by an HMAC we control - a webhook signature and the signed install state - because neither request can carry a session); anything else under `/api` is operator-only until deliberately opened. Operators authenticate against the `AuthAgent` under reserved project id `console`. **The first-run claim requires proof of deployment control** (`src/lib/server/console-setup.ts`, 2026-08-15): it used to be gated on `count(user) === 0` - a fact about the WORLD, not about the claimer - so whoever reached an unclaimed install's `/login` first became its `admin` over every operator surface, and a stock deploy's workers.dev name is guessable (`cloudflarebase`). This was live and exploited against a third party's install before it was fixed; `docs/advisories/2026-08-15-console-claim.md` is the advisory draft. The proof is `CONSOLE_SETUP_TOKEN` (`wrangler secret put`, 24-char minimum, refused shorter rather than accepted as a guess): `POST /api/console/setup` verifies it and mints a 30-minute HMAC-signed grant cookie keyed BY THE TOKEN ITSELF - so nothing is stored server-side and rotating the token revokes every grant - and the cookie is `SameSite=Lax` because the OAuth callback returns as a top-level navigation with no way to resubmit a token. A deploy-window alternative (claimable for 30 minutes after `CF_VERSION_METADATA.timestamp`) was built and then REMOVED: it is a shorter race, not the absence of one. Enforcement is in the GUARD, not the proxy route, because sign-up, `sign-in/social` and `callback/*` are reachable through the `/agents/*` passthrough too and both doors classify public; the matcher decodes and normalizes first, since the proxy rebuilds its target from a DECODED route param (`sign-up%2Femail` is one segment to the guard and two to the agent - the same guard-versus-proxy gap as the encoded traversal). It only ever refuses while the console is UNCLAIMED, so ordinary sign-in pays nothing, and `consoleOwnerState` answers `claimed|unclaimed|unavailable` (503, never 403 - the three-answer rule again) with `claimed` memoized 60s per isolate so a public-signup console doesn't re-read the operator list on every sign-in. `CONSOLE_SETUP_UNLOCKED=true` switches the gate off for the dev loop and is honoured ONLY on a loopback hostname, so copying env.local's vars into a real config cannot disable it. Recovery for a console someone else claimed: `DELETE /api/console/setup` (token grant + `confirm: erase-console-operators` + same-origin when an Origin is present) erases the console AuthAgent and releases every registry row's `org_id`, because the orgs died with it and the guard would otherwise refuse those projects to everyone; it erases the AUTH agent only (the console is not a project - fanning out made a reset that had already destroyed the accounts answer 502 for an unrelated agent being down) and releases orgs only after the erase succeeds. Refused outright on an `open`-signups console: that shape is multi-tenant, where wiping every operator is an outage, not a recovery. Pinned by `e2e/console.setup.ts` (claim refused before unlock, encoded spellings included) and `e2e/security.api.spec.ts`. Registration follows the agent's `CONSOLE_SIGNUPS` (see Managed service below); the agent enforces it on the sign-up route AND in the user-creation database hook, because social sign-in creates users implicitly on the OAuth callback. `/login` reads the console's public `/config` for social buttons and the effective sign-up mode; console Google/GitHub sign-in comes from env secrets on the AUTH worker (`GOOGLE_`/`GITHUB_CLIENT_ID`+`_SECRET`, console instance only - per-project credentials via admin settings cover everything else), the buttons also render on the first-run claim (the provider account becomes the owner), and OAuth callback failures bounce back to `/login?error=<code>`. Better Auth is mounted at the PUBLIC proxy basePath `/api/projects/<pid>/auth` (the agent rewrites its internal `/api/auth/*` dispatch), so emailed verification/reset links and OAuth redirect URIs resolve to the public-by-exception route instead of the guard's 401 - register OAuth apps with redirect URI `<origin>/api/projects/console/auth/callback/<provider>`. Under `DEMO_MODE` a claimed-mode console refuses the owner claim entirely and `/login` explains that instead of offering a doomed form. `/login` resolves the session ITSELF (it is an open route the guard never resolves; signed-in visitors 303 to `?next=`), and carries the full password story: "Forgot password?" → Better Auth `request-password-reset` (the emailed link lands back on `/login?token=` where the reset form completes it) - except when the agent's `/config` reports `localPasswordReset` (DISABLE_EMAIL_VERIFICATION, env.local only: reset mail only lands in .eml files), where the form resets directly via the agent's flag-gated `POST /api/auth/local-reset-password` (404 everywhere else - token-less reset is account takeover). Operators edit their account through the shared `account-menu.svelte` avatar dropdown (header of both shells; it also holds Sign out): name via `update-user`, email via `change-email` (enabled in the agent; verified accounts approve from the CURRENT address), pictures arrive with social sign-in only until R2. **Auth-adjacent navigations are ONE goto with `invalidateAll: true`, never invalidateAll-then-goto**: invalidating while still on the page re-runs its loads mid-flight - the login page's own redirect raced to `/undefined`, and sign-out on a demo deployment minted a throwaway project before `/login` landed. Two distinct surfaces: anonymous demo and session-gated dashboard.
- **Managed service Phase A: accounts, organizations, ownership** (`docs/managed-service-design.md`, implemented; B = hosting implemented below, C/D deferred). `CONSOLE_SIGNUPS` on the auth worker selects console registration: unset/`claimed` (self-hosted default) keeps the single-owner claim but admits sign-ups whose email holds a pending org invitation - teams without open registration, checked BEFORE the demo refusal so cloudflarebase.com (claimed+demo today) can invite; `open` is public sign-up with required email verification + implicit social sign-up, and only takes effect while mail is configured (Cloudflare Email Service: the `EMAIL` binding + `EMAIL_FROM` - it delivers to arbitrary recipients) - otherwise sign-up 503s loudly and `/config` keeps reporting `claimed`. cloudflarebase.com's mail was already configured, so setting the var WAS the launch switch: **it flipped to `open` on 2026-08-13 and cloudflarebase.com now takes public sign-ups.** The backfill was a no-op (the production registry held zero rows - a demo-only console never minted a named project), and `DEMO_MODE` stays on, so anonymous throwaway projects coexist with real accounts. Note the trap that made the flip necessary: a claimed+demo console refuses the owner claim on BOTH paths (route and `denyUserCreation`), so `/login` had no form to offer and rendered the "this is a demo deployment" dead end to everyone, founder included - `claimed` + `DEMO_MODE` is a console that can never have a first operator. The Better Auth `organization` plugin ships in `@cloudflarebase/auth` for every project (anonymous users excluded from org creation); the console instance additionally gets `autoPersonalOrg` (every account lands owning a personal org; `ensurePersonalOrg` also heals pre-org owners lazily in `/console/me`) and a 60s `cookieCache`. **Ownership**: `project.org_id` on the registry (NULL = legacy/self-hosted row, visible to any operator - a claimed install never notices ownership exists); creation stamps the creator's active org, branch rows copy the root's, and the guard requires membership in the owning org on `/api/projects/<id>/**`, `/agents/*`, dashboard pages, AND `/api/registry/projects/<id>/**`. **A registry row is what makes a project** (2026-08-13): an id with no row is refused, because reaching one used to MINT a backend by URL - the agents provision a Durable Object on first touch, so `/dashboard/<anything>` handed any signed-in account an auth stack and a database outside every ownership check and every per-org ceiling, and two accounts typing the same id landed in the same data. Not-yours, not-registered, and reserved all answer the SAME `noSuchProject` (404 for APIs, /dashboard bounce for pages) - a 403 on a project someone else owns would confirm it exists, which is an enumeration oracle for other tenants' ids. The ownership lookup answers `unavailable` when D1 is unreachable (it used to fail open to pre-A behaviour, which under this rule would lock everyone out instead) and the guard 503s for a retry. **Demos are never claimable** (the "Keep this project" claim flow was REMOVED 2026-08-12 - it complicated every demo gate for a bridge nobody needed): demo-shaped ids are never registry rows (`createProject` refuses them), so there is no agent claim route, no claimed flag, no manifest `claim` entry, and the guard treats every demo-shaped id as anonymous throwaway state. UI: org switcher + invitation accept on the projects overview (`/dashboard` always renders the overview - it used to auto-forward into a lone project, which made "All projects" a dead link once every account owned a personal org), `/dashboard/organization` (members/invite/rename over the console auth proxy - `organization` is now a reserved project id, all three mirrors). One-time cloudflarebase.com backfill: `scripts/backfill-org.mjs` stamps pre-org rows with the founder's personal org. Pinned by `e2e/orgs.api.spec.ts` (claimed-mode contract; open mode would need a second differently-configured stack).
- **Managed service Phase B: hosting on Workers for Platforms** (`docs/managed-service-design.md` Phase B, implemented 2026-08-12; mechanism details in `agents/hosting/CLAUDE.md`). An "app" is one user Worker in a dispatch namespace: static assets and/or a bundled Worker, one deploy. **The script name IS the full subdomain** - serving takes the first `*.cfbase.dev` host label into `env.DISPATCH.get(label, {}, { limits: { cpuMs: 50, subRequests: 50 } })`, zero lookup, and NEVER parses app/branch apart; the control plane resolved that at deploy time. **Subdomain scheme**: root deploys serve at `<app>.cfbase.dev`, branch `<root>--<b>` at `<app>-<b>.cfbase.dev` (single dash; `main` aliases the root and never appears). **Claims are control-plane D1** (`app` table; `resolveAppClaim` in `src/lib/server/hosting.ts`): taken names auto-number to the first free `<wanted>-2`, `-3`, ... - never fail - and the resolved subdomain is persisted per project+app on first claim and reused verbatim forever. The console pushes the claim to the agent (`PUT /internal/projects/:id/apps/:app`, service-binding-only) BEFORE forwarding a deploy, so the agent can only ever deploy to subdomains recorded for that project - never trust a subdomain from a caller. **Deploy tokens** (`deploy_token` table, SHA-256 digests only): `cfbd_` bearers the guard accepts SOLELY on `POST .../hosting/apps/<app>/deploys` and `POST .../branches` for the token's root family (`isDeployTokenSurface`; anything else is a plain 401, never a session) - minted/revoked on the Hosting page, roots only. **GitHub deploys** are a GitHub App: one install, no YAML the operator ever writes, still no build farm (2026-08-13). Two modes, inspected at connect time and overridable - `build` (a `build` script exists, so GitHub's runners build it) has the App write `.github/workflows/cloudflarebase.yml` (`contents: write`) and stores NO secret, because the workflow declares `id-token: write` and the console verifies the Actions OIDC token against GitHub's JWKS (`src/lib/server/github-oidc.ts`; the npm-trusted-publishing mechanism); `direct` (committed HTML or a committed output dir) needs no runner AND no file in the repo - the push webhook hands the commit tarball to the agent. Unreadable repos fall back to `build`, which reports problems instead of publishing the wrong tree. **Connect inspection resolves a framework preset** (2026-08-15, `src/lib/server/frameworks.ts` - pure, pinned by `npm run test:unit`): package.json deps + root listing → prefilled build command, output dir, and package-manager-matched install steps (pnpm/yarn/bun detected from lockfiles; pnpm and bun skip setup-node's cache since the binary lands after it), all editable in the connect dialog and written into the workflow (`buildCommand`/`assetsDir`/`rootDir` persist on `github_connection`; the output dir travels as `CLOUDFLAREBASE_ASSETS`, which the CLI already read). **Root directory** (monorepos, build mode): inspection re-reads the SUBDIRECTORY on field change (`?dir=` on the repos route; lockfiles union the repo root's, since workspaces keep one at the top; a missing dir warns and blocks Connect), and the workflow scopes install/build/deploy with `working-directory` while PREFIXING every `hashFiles` guard - hashFiles always resolves from the workspace root, working-directory or not. Detection prefers loud failure over silent wrong deploys: Next-without-OpenNext states `out` so the deploy fails naming the real problem instead of autodetecting the repo's `public/` SOURCE dir, adapter-auto SvelteKit gets a note (it detects nothing on a plain runner and builds nothing deployable), and wrangler-driven presets (OpenNext, adapter-cloudflare, Astro SSR) leave the output dir to the repo's own wrangler config - **which connect COMMITS when the repo has none** (`WRANGLER_TEMPLATES`/`wranglerConfigJsonc`: server-generated from a fixed map, never client content; committed BEFORE the workflow so the workflow's own trigger push already builds against it; existence re-checked server-side at connect so a config pushed since inspection is never overwritten; disconnect leaves it - it is the user's build setup now). - **Service keys: the credential a SERVER holds** (`docs/service-keys-design.md`, SK1 implemented 2026-08-16). The product was client-first: a browser app needs no API key BY DESIGN (the signed-in user's own project JWT is the credential) and an SSR route can RELAY the identity the user already sent it (`/auth/token` accepts a bearer session token, not just a cookie - the Integration tab's Server snippet). But a cron, a queue consumer, a webhook handler, or a seed script has NO user to relay, and the only credential that would have worked was an operator session: the whole account, sliding 30 days, unscoped. `cfbs_` keys close exactly that gap. **This is an AUTHENTICATION change, not an authorization one** - every agent already serves mode-bypassing operator routes with Admin-SDK semantics, and until now only a human session could reach them, so there are zero agent changes and no new bypass path. Minted per project on Settings (one-time reveal, SHA-256 digests only, 5 per project), scoped to **ONE registry row and never the root-plus-branches family deploy tokens use** - for data the branch IS the isolation boundary. Accepted on `db/**`, `storage/**`, auth `admin/**`, `/overview`, `/analytics` (`isServiceKeySurface`); refused everywhere else, so a key cannot mint another credential, re-role an operator, deploy, or delete its own project. **Any request carrying an `Origin` is refused outright** - server fetches send none and browsers always do, so a key pasted into frontend code fails at the developer's desk instead of shipping in a JS bundle; a present-but-empty Origin counts as absent (a browser cannot produce one, an HTTP client can). **No verification cache**, deliberately: the draft had a 30s isolate cache, but every surface a key opens is a parent-mediated DO hop that dwarfs an indexed D1 read, so the cache only bought revocation latency on the most powerful credential in the system - revocation is now instant. Pinned by `e2e/service-keys.api.spec.ts`, where every containment test proves the key is LIVE in the same context first: the first green run was green on nothing, because all its assertions expected 401 and the key was being refused for an unrelated reason.
- **The server-side service path: complete the API, do not wrap it** (`docs/admin-sdk-design.md`, A1-B implemented 2026-08-16). SK1 shipped the credential and stopped; SK2 was scoped as a `@cloudflarebase/db/admin` package plus a storage twin. **That was reversed**: the key is verified in the CONSOLE guard, and `isServiceKeySurface` matches only under `/api/projects/<id>/`, so the request reaches each agent over a service binding the console already authorized - the agents never see a `cfbs_` bearer and a key does not work on `/agents/*` at all. One key, one origin, every primitive, before any client code exists; a package would re-describe a unified surface rather than create one, and `@cloudflarebase/db/admin` specifically would ship - inside the db package - a client that never calls the db worker. The generated OpenAPI document is the reference and cannot drift from the routes, where a hand-written client would. So: **no package; fix the API and document it.** Three holes were closed. **Storage objects were unreachable by a key** - the agent always served `/admin/buckets/:b/objects[/:key]`, but the console proxied only bucket CONFIG (deliberately: "bytes never transit this proxy, its handlers buffer bodies"), and that premise expired when service keys shipped a day after storage, since the console UI and the whole e2e suite reach objects through `/agents/*` and a key cannot. The new `[...key]` proxy STREAMS `request.body` to the binding rather than buffering, because a proxy that buffers a 100 MB PUT reintroduces the memory bomb the agent's `Content-Length` requirement (411) exists to prevent. **A db record could be written and never read back**: the item routes were PUT+DELETE only and `/admin/query` cannot filter `id` (every `where.field` compiles to a JSON path into `data`; `id` is a system column), so both kinds gained `adminGet`/`adminPatch` - PATCH merges and NEVER creates. Tables had an accidental escape hatch in `/admin/tables/:name/sql`, which takes no JWT; raw SQL is not an API for a single-row read. **Auth could not create a user** - the surface listed, re-roled, and deleted, so seeding, invite-first products, and provider migrations were impossible; `POST /admin/users`, `GET|PATCH /admin/users/:id`, and `PUT /admin/users/:id/password` now run over Better Auth's `internalAdapter`. Creation bypasses sign-up MODE and verification (the Admin-SDK contract, with an explicit `emailVerified` defaulting to false) but NOT the user-creation database hook, so demo caps and the console's refusal still apply. `role` is absent from the general PATCH so `/role` stays the single writer and the console lockout guards cannot be walked around. **The reference had no `serviceKey` security scheme at all**, so the artifact this whole decision rests on never mentioned that server-side access exists; `OPERATOR_SECURITY` now marks exactly the routes `isServiceKeySurface` admits and `/chat` deliberately keeps `sessionCookie` alone. Two traps worth remembering: SvelteKit routes by EXPORTED method, so a catch-all proxy still 405s an unexported verb; and **CSRF refused the primary server path**, which is now fixed. SvelteKit's check runs before every hook and forbids form content types (`text/plain`, `multipart/form-data`, `x-www-form-urlencoded`) when there is no Origin - exactly a service key's shape, since the guard refuses the key if one IS present. And `fetch` defaults a string body to `text/plain;charset=UTF-8`, **`JSON.stringify(...)` included**, so the most natural call a server can write answered 403 before the key was read; it was first mis-scoped as a storage-only wart (where `text/plain` is legitimate CONTENT rather than a forgotten header). `csrf.checkOrigin` is therefore OFF in `svelte.config.js` and re-implemented as `csrfHandle`, FIRST in the hook sequence to keep SvelteKit's ordering guarantee: SvelteKit's exact rule, skipped in exactly one case - the request carries a BEARER-shaped `Authorization` header (`/^Bearer\s+\S/i`, tightened 2026-08-18: every credential this app accepts is a bearer, while `Basic` is one a browser CAN attach by itself - a `user:pass@host` top-level navigation - beside the victim's cookies, which the guard would then authenticate). Sound because CSRF depends on the browser supplying the credential BY ITSELF: cookies do, a bearer does not (a browser never adds one, and a cross-origin fetch that sets one triggers a preflight this app does not answer), and an attacker who knows the bearer has no use for CSRF. Never disable one without the other. The two halves are pinned apart because the relaxation is the dangerous one: `service-keys.api.spec.ts` proves a bearer write with `text/plain` works, `security.api.spec.ts` proves foreign-origin AND origin-less cookie form writes still 403 across all three content types (sign-in included, `Basic` Authorization included) with a same-origin control. **Each agent package then ships an `./admin` subpath over that API** (`@cloudflarebase/db/admin`, `/auth/admin`, `/storage/admin`; raw HTTP stays the contract and stays documented). They live in the agent packages, not a standalone one, because an admin client wraps THAT agent's admin routes - so a route and its client ship in one version, the same drift-prevention property the generated reference has. `createDbAdmin()` and friends resolve url/project/key most-explicit-first from options → a passed `env` → the ambient process (`CLOUDFLAREBASE_SERVICE_KEY` canonical - the sibling credential is already `CLOUDFLAREBASE_DEPLOY_TOKEN` - with `CFBASE_SERVICE_KEY` accepted; a Worker has no global `process`, so pass `{ env }`). They target the CONSOLE origin, never an agent base. Three things they do that raw fetch cannot, which is why they exist at all: **refuse to construct in a browser** (`typeof globalThis.document !== 'undefined'` - never `window`, the Workers types declare no DOM) with an error naming the client to use instead; throw **`DbAgentTooOldError`/`AuthAgentTooOldError`** when a 404 is not the agent's own `no such ...` answer, because a routing 404 from an older deployed agent is otherwise indistinguishable from a missing record and acting on that is data-loss-shaped; and refuse form content types locally with the reason. Pinned by `e2e/service-keys.api.spec.ts` (every password proven by a real sign-in through the public route - the only thing that shows the hash is Better Auth's), `e2e/admin-sdk.api.spec.ts` (drives the REAL exports, never re-implementing their URLs), and `e2e/openapi.api.spec.ts`.

- **Storage on R2** (docs/storage-agent-plan.md; S1 shipped 2026-08-15 with S2's access modes, JWT gate, and serve-time policy pulled forward; mechanism details in `agents/storage/CLAUDE.md`). A separate agent - R2 is an account-level checkout opt-in, so a binding on the db worker would break every `@cloudflarebase/db` install (the AUTH_EVENTS lesson) - on **one shared R2 bucket, key-prefixed `p/<projectId>/<bucket>/<key>`**: the prefix is the ONLY tenant boundary, so keys are validated (never repaired - no dot/empty segments, no control chars, 1024-byte composed ceiling) and **the bucket must never carry r2.dev or a custom domain** (either serves every tenant raw; cdn.cloudflarebase.com is a WORKER route + `STORAGE_SERVE_DOMAIN`, GET/HEAD only). Bytes never enter a DO: the worker streams to R2 and RPCs the `StorageBucket` index (sorted keyset paging, counters) after - R2 first on writes AND deletes, so crashes leave benign phantom rows, never billed-forever orphans. Per-bucket `read`/`write` modes `public|auth|owner` **default `auth` both ways** (never anonymous by accident), `publicListing` is a separate grant, permission keys 403 on valid-but-unentitled tokens, and `owner` stamps/checks the JWT subject in R2 customMetadata (not-yours = 404). ## Gotchas

- DO SQLite blocks `pragma_table_info()` and explicit `BEGIN`/`COMMIT` with `SQLITE_AUTH`. No Better Auth Kysely migrations; Drizzle migrations with `transaction: false`.
- Miniflare service bindings are realm-sensitive: call `binding.fetch(url, init)`, never a Node-realm `Request`, and convert responses with `toNativeResponse` before returning from SvelteKit.
- **WebSocket upgrades can never go through a `+server.ts` proxy.** A 101 carries a `webSocket` and a status `new Response` refuses, so `toNativeResponse` re-wrapping one throws `RangeError` - which is how a client that dialled `/api/projects/<id>/db/collections/<c>/subscribe` (instead of letting the SDK rewrite to `/agents/...`) got a 500. `applicationHandle` forwards any `Upgrade: websocket` request on `/api/projects/<id>/<prefix>/**` straight to the agent binding, untouched, exactly like `/agents/*` and still behind the guard; `toNativeResponse` passes an out-of-range status through instead of throwing. Pinned by the proxy-base subscribe test in `e2e/db-live.api.spec.ts`.
- **Never interpolate a decoded route parameter into an agent URL.** SvelteKit decodes route params, so `%2F` arrives as a real slash and `%2E%2E` as a real dot segment; string-interpolating one into a URL hands the URL parser a traversal, which it resolves. `/api/projects/<id>/auth/..%2F..%2Fadmin%2Fusers` therefore normalized to `/agents/auth-agent/<id>/admin/users` and answered **200 to anyone** - the guard had classified the request PUBLIC from its `auth/` prefix, because the raw path it inspects keeps `%2F` inside one segment while the proxy's rebuild does not. One more level crossed into another project. Fixed 2026-08-13 by `agentProxyUrl` in `src/lib/server/agents.ts`: build from a FIXED prefix plus the untrusted rest, normalize with `new URL`, then require the result to still sit under that prefix - encoding-agnostic, because the check runs on the path the agent will actually see. Single-segment ids go through `agentSegment` (`encodeURIComponent` hides the slashes but leaves `..` intact). Pinned by `e2e/security.api.spec.ts`. The `/agents/*` passthrough was never affected: it forwards the request untouched, and `event.url.pathname` is already normalized before the guard reads it.
- **Agent proxies must never follow agent redirects.** fetch defaults to `redirect: 'follow'`, and a service-binding fetch replays the Location against the same binding - the agent worker sees a non-`/agents/*` path and answers its own 404, and any Set-Cookie riding the 302 is swallowed with it. Better Auth answers OAuth callbacks and emailed links with 302s the BROWSER must follow, so the auth `[...path]` proxy forwards with `redirect: 'manual'`. The `/agents/*` passthrough was never affected (an incoming workerd Request already carries `redirect: 'manual'`), and dev masked the bug: miniflare's binding proxy follows the Location over real HTTP through Vite, which happens to land on Better Auth's error page. Pinned by the callback-redirect test in `e2e/auth-flow.api.spec.ts`.
- Run agent Wrangler commands from the agent's own directory - `agents/auth`, `agents/db`, `agents/storage`, or `agents/hosting` (at the root they target the web Worker). `--env preview` targets the `-preview` worker.
- Deploy order is auth → db → storage → hosting → web (`deploy:all` encodes it): the db and storage workers' `AUTH_AGENT` service bindings and the web worker's agent bindings each need their target to exist first. For cloudflarebase.com the hosting agent additionally needs `hosting-outbound` deployed first (its `deploy:production` encodes that) and the `cfbase.dev` zone to exist before `env.production` can claim its wildcard route.
- `BETTER_AUTH_SECRET` is a plain var only in local/test; `wrangler secret put` elsewhere. Analytics writes need no token; SQL reads need `CF_ACCOUNT_ID` + `CF_ANALYTICS_API_TOKEN` (Account Analytics Read).
- **Analytics Engine is an account-level opt-in with no API**, so nothing that must deploy on a fresh account may declare it. Enabling it is a dashboard-only action (free); there is no `wrangler` flag, and Cloudflare refuses the SCRIPT UPLOAD rather than the write - `no_access_to_analytics_engine`, code 10089. The auth agent's `AUTH_EVENTS` binding is therefore OPTIONAL and absent from both the self-hosted top level of `agents/auth/wrangler.jsonc` and the CLI's `template/wrangler-fragment.jsonc` (2026-08-15); cloudflarebase.com's own environments declare it. Requiring it meant `npm run deploy:all` died on the very first Worker in the chain for anyone who had never enabled it - in exchange for datapoints that an install without `CF_ACCOUNT_ID`/`CF_ANALYTICS_API_TOKEN` could never read. Runtime never needed it: `writeDataPoint` is called through `this.env.AUTH_EVENTS?.`.
- Never hand-edit generated `worker-configuration.d.ts`; regenerate, and put optional-secret augmentations in a separate `.d.ts`. Both generated files are lint-ignored.
- `checkJs` stays off in the root tsconfig: `wrangler types` emits `GlobalProps.mainModule` as `typeof import()` of the **built** bundle, so with `checkJs` on any tree that has run a build gets thousands of junk errors from type-checking `.svelte-kit/cloudflare/_worker.js`.
- The agent entrypoint may only export handlers and DO classes. A value export fails at boot with `Incorrect type for map entry`, which reads like a config error. Type-only exports are fine.
- **Sentry only sees errors that ESCAPE.** `handleErrorWithSentry` never fires for SvelteKit's `error(status, ...)` (an `HttpError` is returned to the client without reaching the hook), and the Worker/DO instrumentation only catches throws - so anything caught and turned into an error response, or degraded into an empty/null payload, is invisible. Use `serverError()` from `src/lib/server/agents.ts` instead of `error()` for 5xx, and capture explicitly before returning a degraded result. The agents' worker entrypoints additionally report every response `>= 500` (the db worker's hot path included), wrapped so reporting can never replace the response.
- Sentry DSNs stay empty in the top-level self-hosted defaults - a DSN there would collect every fork's errors, and empty disables reporting. cloudflarebase.com's own `env.production`/`env.preview` blocks carry real DSNs on purpose: those blocks are not deployed by forks, and a DSN is browser-visible by design anyway. **`SENTRY_DSN` is a VAR, never a secret** (2026-08-15): every config and CLI fragment declares it in `vars`, which wrangler uploads as a `plain_text` binding of that name, so a `wrangler secret put SENTRY_DSN` is overridden by the empty var on the next deploy - which is exactly what six comments told self-hosters to do. It is also absent from every manifest's `secrets.optional` for the same reason (`docs/agent-contract.md` carries the rule: `secrets` is only for values that must not be readable). Wholly optional either way - reporting is simply off until a DSN is set, and `secrets.required` stays `[]` in all three self-hosted defaults. That field is real: wrangler 4 reads `secrets.required` and adds an `inherit` binding per name, and it FAILS a first deploy when one is unset - so listing an optional value there would break a fresh install the way the required `AUTH_EVENTS` binding did.
- **Two unrelated rate limits, don't confuse them.** `API_RATE_LIMITER` (a Workers rate-limiting binding, all five `ratelimits` blocks in `wrangler.jsonc`, applied in `apiRateLimitHandle`) is per-IP over `/api/*` — which includes the REST **proxy base**, so it is an application throughput limit, not a console one; it is 1000/10s (100 req/s per IP, up from a 100/60s that was 1.7 req/s and 429'd real apps). The sizing constraint is the SHARD, not the console: a Durable Object is single-threaded at ~1k req/s, so a per-IP allowance near that would let one client saturate a whole project. Cloudflare accepts `period` of **only 10 or 60**, and the counter is per **Cloudflare location**, not global, so one key accumulates independently per colo and this can never be sized as a hard global cap. Keying on IP is an abuse ceiling, not fair-share (a customer's server-side backend is thousands of end users behind one IP) - real per-tenant throughput limiting belongs per project. `/agents/*` bypasses it entirely, which is why the SDK hot path is unaffected. Better Auth's limiter (`agents/auth/src/auth.ts`) is separate, covers `/api/auth/*` only, and stays tight on sign-in/sign-up (10/min) because it is anti-credential-stuffing, not throughput — but `/get-session` is not a guessing surface and gets 2000/min, because the console guard reads it on every request and the default 100/min signed operators out mid-session (see Console auth). Neither raises the real ceiling: a Durable Object is single-threaded at ~1k req/s per instance, and you scale past that by sharding, region replicas, and gateway siblings.
- **GitHub App keys are PKCS#1; WebCrypto imports only PKCS#8.** GitHub's "generate a private key" hands you `BEGIN RSA PRIVATE KEY`, and `crypto.subtle.importKey('pkcs8', ...)` rejects it with a message that reads like a corrupt key. `src/lib/server/github.ts` wraps PKCS#1 in a `PrivateKeyInfo` (a fixed DER prefix plus the original bytes) so the key can be pasted verbatim - never add an `openssl pkcs8` setup step. Webhook HMAC must be computed over the RAW request body: `JSON.stringify` of a parsed payload does not reproduce GitHub's bytes, so the route reads `text()` first and parses after verifying.
- Lucide dropped its brand icons, so there is no `Github` export - use `GitBranch`. And never bulk-rename with PowerShell `-replace`: it is case-INSENSITIVE by default, so `Github` also matches `github` in paths, testids, and prose.
- `TRUSTED_ORIGINS` is only for origins other than the deployment's own (the agent trusts its own origin automatically). A cross-origin request from an unlisted origin gets an explicit 403 `INVALID_ORIGIN`, never a credential error.
- On Windows, killing only a listening workerd leaves its Wrangler parent alive with children that lock persistence dirs. `scripts/kill-port.mjs` kills the full tree (match scoped to Wrangler); `scripts/clean-dir.mjs` only accepts `.wrangler/test-state` targets and retries `EBUSY`/`EPERM`.
- **A deploy breaks every tab that is already open** (2026-08-17). Workers static assets are versioned WITH the Worker, so a deploy replaces the whole asset manifest and the previous build's hashed chunks 404 immediately - there is no retention window the way there is on hosts that keep old deploys served. An open tab therefore holds a module graph the origin can no longer serve, and its next `import()` rejects: `TypeError: Failed to fetch dynamically imported module .../_app/immutable/nodes/6.<hash>.js`, which is what a month of Sentry regressions on `/(marketing)` actually were. SvelteKit already recovers a real NAVIGATION (it re-reads `_app/version.json` and hands off to the browser), so what escapes is the hover PRELOAD (`data-sveltekit-preload-data="hover"` in `app.html`) - it reports through `handleError` and skips the version check - plus every dynamic import SvelteKit does not own (Scalar on the API page, shiki behind the code samples). Three parts, all in `$lib/stale-build`'s orbit: `version.pollInterval` (5 min) lets a tab NOTICE a deploy on its own, the root layout's `beforeNavigate` then hands the next navigation to the browser BEFORE an import can fail, and `hooks.client.ts` drops the stale-chunk error from Sentry only once `updated.check()` proves a newer version is live. That proof is the whole design: the same rejection under an UNCHANGED version means a broken deploy, and reloading on that would loop instead of heal. Invisible in `vite dev`, where SvelteKit stubs `updated.check()` to false and no build ever goes stale. **The reason RELOADING did not fix it is a second defect, in the response headers**: SvelteKit sets no cache headers on a rendered page and neither did this app, so the document went out with no freshness information AND no validator - `Date` and `Content-Type` and nothing else - which is exactly the shape RFC 9111 lets any cache assign an invented lifetime to, with nothing to revalidate against. The browser then served the same stale HTML, naming the same dead chunks in the same `Link: rel=modulepreload` list, until the cache was wiped. `documentCacheHandle` sets `private, no-cache` on any HTML response that did not already claim the header: revalidate rather than `no-store` (which would also cost the back/forward cache), and `private` because every page here varies by session. The DOCUMENT was the only thing left bare - SvelteKit already answers `__data.json` with `private, no-store`, redirects are not heuristically cacheable at all, and hashed assets never reach this Worker, their year-long immutable max-age being correct precisely because their URL changes when their content does.
- Workers Builds is connected to the single web Worker `cloudflarebase-com`: the production branch deploys `--env production`, non-production branches upload preview **versions** with `--env preview`. Every command CI runs must resolve the name `cloudflarebase-com` - a "Failed to match Worker name" warning means the resolved config name and the connected Worker disagree, and never merge the automated rename PR Workers Builds offers. Corollary: `wrangler deploy --env preview` from a machine would live-deploy preview bindings (the preview agent!) onto production - preview goes out only as `wrangler versions upload --env preview`, which is why no npm script wraps it.

## Conventions

- Svelte 5 runes, shadcn-svelte under `$lib/components/ui`, LayerChart, `mode-watcher`, tabs, single quotes.
- Routes are grouped: `(marketing)` holds the landing page and the `(legal)` subgroup (`/privacy`, `/terms` — prose mapped onto shadcn tokens in the subgroup layout); `(app)` holds `login`, `admin`, `dashboard`. The legal pages describe cloudflarebase.com's actual demo-mode behavior (no accounts, no emails collected, analytics fields, retention) — recheck them when data handling changes. `api/` and the root layout/error stay ungrouped (groups do nothing for `+server.ts` routes but would churn their route ids). Groups appear in `resolve()` route ids (`/(app)/dashboard/[projectId]`), never in URLs.
- Dynamic segments are named for what they hold: `[projectId]`, `[userId]`, `[sessionId]`, never `[id]`.
- New primitives follow the agent contract (`docs/agent-contract.md`): separate npm project under `agents/<name>` shipping a `cloudflarebase.agent.json`, DO classes with `routeAgentRequest` entrypoint, root service bindings per environment, one entry in `src/lib/agent-registry.ts` (which drives guard, dispatch, proxies classification, sidebar, fan-out) plus an `src/lib/openapi/<name>.ts` module, proxy routes under `api/projects/[projectId]/<prefix>/`, one `AGENTS` record entry in `cli/src/lib/agents.ts`, and the four CI touchpoints (`.github/workflows/<name>-agent-deploy-{prod,preview}.yaml`, the `release.yaml` package list + `<name>-v*` tag trigger, `quality.yaml` typecheck + unit test).
