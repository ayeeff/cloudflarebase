# Cloudflarebase

Firebase alternative built natively on Cloudflare (Workers, Durable Objects, D1, KV, R2, Workers AI, Agents SDK). Agent-first: each backend primitive is a Cloudflare Agent, one Durable Object instance per client project.

Also read [AGENTS.md](AGENTS.md). Cloudflare APIs change frequently; retrieve current official documentation before Workers, Durable Objects, Agents, bindings, or limits work.

## Repository layout

Separate npm projects with separate Wrangler configs and generated `Env` types. Never import runtime code or generated Worker types across them. Shared DTOs are deliberately copied and must be kept in sync.

| Path          | Worker                                                         | Purpose                                                                                                                                                                                                                   |
| ------------- | -------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `/`           | `cloudflarebase` (`cloudflarebase-com` in `env.production`)    | SvelteKit 2/Svelte 5 dashboard and marketing site, shadcn-svelte, Tailwind v4, Cloudflare adapter                                                                                                                         |
| `agents/auth` | `auth-agent` (`-local`, `-test`, or `-preview` by environment) | `AuthAgent` Durable Object, one per project; Better Auth and Drizzle over embedded DO SQLite                                                                                                                              |
| `agents/db`   | `db-agent` (`-local`, `-test`, or `-preview` by environment)   | `DbAgent` (coordinator, one per project) + `DbCollection` (one per collection) + `DbTable` (one per SQL table) + `DbGateway` (one-socket realtime, per region): documents and typed-column tables, both with live queries |
| `agents/hosting` | `hosting-agent` (`-local`, `-test`, or `-preview`), plus `hosting-outbound` (own tiny worker, `wrangler.outbound.jsonc`) | `HostingAgent` Durable Object, one per project: apps and functions on Workers for Platforms - deploy orchestration in the DO, `*.cfbase.dev` wildcard serving in the same worker (docs/managed-service-design.md Phase B) |
| `cli`         | none (Node on the consumer's machine)                          | `@cloudflarebase/cli`, the `cloudflarebase` bin: `init` / `add <agent>` / `link` / `deploy` / `secret set` / `login` / `logout` / `schema generate\|apply\|drop` (docs/schema-cli-design.md)                              |

The root Worker binds `AUTH_AGENT` + `DB_AGENT` + `HOSTING_AGENT` (agent services) and `DB` (control-plane D1). Agent instances live at `/agents/<worker>/<projectId>/...`.

**Every agent ships a `cloudflarebase.agent.json` manifest** (`docs/agent-contract.md`, implemented). The app imports those files directly from `agents/<name>/` into `src/lib/agent-registry.ts` - single-sourced on purpose, so the console guard can never drift from what the package declares - and the guard route table, `/agents/*` dispatch, `/api/projects/<id>/<prefix>/*` proxy classification, sidebar navigation, project-delete fan-out, and per-agent OpenAPI modules (`src/lib/openapi/<name>.ts`) are all registry-driven. The CLI reads the manifest from the installed package and derives the entrypoint export lines from it.

**The top level of both Wrangler configs is the self-hosted default, not this project's deployment.** It publishes to workers.dev, claims no custom domain, and leaves `DEMO_MODE` unset so a fresh install is private. cloudflarebase.com lives in `env.production`, deployed with `npm run deploy:production`. The agent's `env.production` name is pinned to `auth-agent` (what the service binding resolves). The web `env.preview` is the **same Worker** as production (`cloudflarebase-com`): previews are versions of it, uploaded by Workers Builds from non-production branches, and the environment exists for its bindings - `AUTH_AGENT` targets `auth-agent-preview` - which versions carry individually.

## Architecture decisions

- **`agents/auth` is published as `@cloudflarebase/auth`.** Supabase's distribution model: the agent is a versioned artifact you depend on, not source you fork. A consumer owns their `wrangler.jsonc` and entrypoint. `files` ships `dist`, `template`, and `NOTICE` only. Mechanism and constraints in `agents/auth/CLAUDE.md`.
- **CI secrets live in GitHub environments, never repository secrets.** The agent deploy workflows declare `environment: production` / `environment: preview` (Cloudflare credentials, branch-restricted to `main` / `preview`), and publishing declares `environment: release`. Quality and e2e run untrusted PR code, so they hold no secrets and `permissions: contents: read`. The d1-migrate workflows were deleted: the control plane applies its schema at runtime, and they referenced a `migrations/` directory and `D1` binding that no longer exist.
- **Releases are merge-driven** (`.github/workflows/release.yaml`). Every push to `main` publishes each package whose `package.json` version is absent from the npm registry - bump on `preview`, merge, done. The registry is the ledger, so runs are idempotent (unchanged versions publish nothing, failed publishes self-heal on the next push, a never-published package ships on its first merge), and the ungated detect job means no-bump merges never ping the release reviewers. Tags (`auth-v*`, `db-v*`, `cli-v*`) remain the manual escape hatch and refuse a tag/package.json mismatch. Every publish runs the full typecheck (which is what executes `bindings.test-d.ts`; the build config excludes it). Publishing is npm trusted publishing (OIDC): no token exists anywhere, npmjs.com accepts only this repo + workflow + `release` environment, whose required reviewers gate every publish. Provenance requires a public repo.
- **The CLI is the delivery mechanism.** `add <agent>` npm-installs the agent, merges its `template/wrangler-fragment.jsonc` (jsonc-parser; comments survive, user values never overwritten, collections merge by binding name, DO migrations append under the next free tag), prepends the entrypoint re-export with the `AssertAuthAgentEnv` check, and reruns `wrangler types`. Every step idempotent. Fragments and templates ship inside each agent's package, so a new primitive is one registry entry in `cli/src/lib/agents.ts`. Agents are DO classes in the consumer's single Worker; `add` never means another deploy. `deploy` deploys once and reports the URL (the agent trusts its own origin, so nothing needs configuring first). `CLOUDFLAREBASE_<AGENT>_SPEC` overrides the install source.
- Drizzle is the database layer (`drizzle-orm/durable-sqlite`); drizzle-kit output is inlined into `src/migrations.ts` as string literals and applied in `onStart`. Inlining instead of `.sql` text modules is what lets the agent ship as a plain npm dependency. Better Auth runs inside each `AuthAgent` with the Drizzle SQLite adapter, `transaction: false`, and project-scoped cookie prefixes.
- Simple RBAC: `user.role` (default `user`) is a Better Auth additional field with `input: false`; the dashboard's `PUT /admin/users/:id/role` proxy is the only writer. Roles are a per-project registry of `{ name, permissions[] }` (`PUT /admin/roles`, agent state, built-in `user`/`admin` always present). The `jwt` plugin issues project-signed JWTs on `GET /token` (keys on `GET /jwks`, keypair in the agent's `jwks` table) with `email`, `role`, and `permissions` claims.
- The browser uses same-origin `/api/projects/<id>/...` SvelteKit endpoints, proxied over `AUTH_AGENT` preserving cookies, origin, and the edge-resolved country header.
- **Console auth.** Every operator surface requires a session, enforced by `consoleGuardHandle` in `src/hooks.server.ts` across `/dashboard/*`, `/api/*`, and the `/agents/*` passthrough (which reaches the DO without a proxy). Sessions resolve from cookies OR a bearer `Authorization` header (the CLI's path); since Phase A the guard resolves the full IDENTITY - session + org memberships + pending invitations - in ONE agent round trip (`getConsoleIdentity` → the agent's `GET /console/me`; 404 falls back to plain get-session with no orgs so a pre-Phase-A agent degrades instead of signing everyone out), memoized as `locals.consoleIdentity` beside `locals.consoleUser`. The CLI login hand-off is `/cli-auth` (operator page; approve form-POSTs the token from `POST /api/cli/token` to the CLI's localhost listener) - pinned by `e2e/cli-auth.{api,ui}.spec.ts`. Public by exception only: `/api/projects/<id>/auth/*`, `/config`, `/openapi.json`; anything else under `/api` is operator-only until deliberately opened. Operators authenticate against the `AuthAgent` under reserved project id `console`. Registration follows the agent's `CONSOLE_SIGNUPS` (see Managed service below); the agent enforces it on the sign-up route AND in the user-creation database hook, because social sign-in creates users implicitly on the OAuth callback. `/login` reads the console's public `/config` for social buttons and the effective sign-up mode; console Google/GitHub sign-in comes from env secrets on the AUTH worker (`GOOGLE_`/`GITHUB_CLIENT_ID`+`_SECRET`, console instance only - per-project credentials via admin settings cover everything else), the buttons also render on the first-run claim (the provider account becomes the owner), and OAuth callback failures bounce back to `/login?error=<code>`. Better Auth is mounted at the PUBLIC proxy basePath `/api/projects/<pid>/auth` (the agent rewrites its internal `/api/auth/*` dispatch), so emailed verification/reset links and OAuth redirect URIs resolve to the public-by-exception route instead of the guard's 401 - register OAuth apps with redirect URI `<origin>/api/projects/console/auth/callback/<provider>`. Under `DEMO_MODE` a claimed-mode console refuses the owner claim entirely and `/login` explains that instead of offering a doomed form. Three distinct surfaces: anonymous demo, `/admin` behind `ADMIN_SECRET`, session-gated dashboard.
- **Managed service Phase A: accounts, organizations, ownership** (`docs/managed-service-design.md`, implemented; B = hosting implemented below, C/D deferred). `CONSOLE_SIGNUPS` on the auth worker selects console registration: unset/`claimed` (self-hosted default) keeps the single-owner claim but admits sign-ups whose email holds a pending org invitation - teams without open registration, checked BEFORE the demo refusal so cloudflarebase.com (claimed+demo today) can invite; `open` is public sign-up with required email verification + implicit social sign-up, and only takes effect while mail is configured (Cloudflare Email Service: the `EMAIL` binding + `EMAIL_FROM` - it delivers to arbitrary recipients) - otherwise sign-up 503s loudly and `/config` keeps reporting `claimed`. cloudflarebase.com's mail is already configured, so setting the var IS the launch switch: it stays out of the committed vars and flips to `open` only after the ownership-aware web worker is deployed and the backfill has run. The Better Auth `organization` plugin ships in `@cloudflarebase/auth` for every project (anonymous users excluded from org creation); the console instance additionally gets `autoPersonalOrg` (every account lands owning a personal org; `ensurePersonalOrg` also heals pre-org owners lazily in `/console/me`) and a 60s `cookieCache`. **Ownership**: `project.org_id` on the registry (NULL = legacy/self-hosted row, visible to any operator - a claimed install never notices ownership exists); creation stamps the creator's active org, branch rows copy the root's, and the guard requires membership in the owning org on `/api/projects/<id>/**`, `/agents/*`, dashboard pages, AND `/api/registry/projects/<id>/**` (403 for APIs, /dashboard bounce for pages; the ownership lookup fails OPEN to pre-A behaviour if D1 is unreachable). **Demo claim**: `claimDemoProject` inserts the registry row under the claimer's org (first-claim-wins by PK; roots only; the ONLY minter of demo-shaped rows - ordinary creation refuses them) THEN fans out `PUT /internal/projects/:id/claim` per the manifest's optional `claim` entry; agents fold a durable claimed flag into `isEphemeral` (caps lift, TTL disarms via the re-check, db children get config re-pushes, the gateway asks the parent). Anonymous access to a claimed family - minted branches included, via the demo-root fallback in `getProjectOwnership` - ends the instant the row exists; `createBranch` fans the claim to demo-shaped branch ids. UI: "Keep this project" on demo surfaces (anonymous → `/login` → back with `?claim=1` which auto-claims), org switcher + invitation accept on the projects overview, `/dashboard/organization` (members/invite/rename over the console auth proxy - `organization` is now a reserved project id, all three mirrors). One-time cloudflarebase.com backfill: `scripts/backfill-org.mjs` stamps pre-org rows with the founder's personal org. Pinned by `e2e/orgs.api.spec.ts` + `e2e/demo-claim.api.spec.ts` (claimed-mode contract; open mode would need a second differently-configured stack).
- **Managed service Phase B: hosting on Workers for Platforms** (`docs/managed-service-design.md` Phase B, implemented 2026-08-12; mechanism details in `agents/hosting/CLAUDE.md`). An "app" is one user Worker in a dispatch namespace: static assets and/or a bundled Worker, one deploy. **The script name IS the full subdomain** - serving takes the first `*.cfbase.dev` host label into `env.DISPATCH.get(label, {}, { limits: { cpuMs: 50, subRequests: 50 } })`, zero lookup, and NEVER parses app/branch apart; the control plane resolved that at deploy time. **Subdomain scheme**: root deploys serve at `<app>.cfbase.dev`, branch `<root>--<b>` at `<app>-<b>.cfbase.dev` (single dash; `main` aliases the root and never appears). **Claims are control-plane D1** (`app` table; `resolveAppClaim` in `src/lib/server/hosting.ts`): taken names auto-number to the first free `<wanted>-2`, `-3`, ... - never fail - and the resolved subdomain is persisted per project+app on first claim and reused verbatim forever. The console pushes the claim to the agent (`PUT /internal/projects/:id/apps/:app`, service-binding-only) BEFORE forwarding a deploy, so the agent can only ever deploy to subdomains recorded for that project - never trust a subdomain from a caller. **Deploy tokens** (`deploy_token` table, SHA-256 digests only): `cfbd_` bearers the guard accepts SOLELY on `POST .../hosting/apps/<app>/deploys` and `POST .../branches` for the token's root family (`isDeployTokenSurface`; anything else is a plain 401, never a session) - minted/revoked on the Hosting page, roots only. **GitHub deploys** ride an official Actions workflow (single-sourced in `src/lib/hosting-workflow.ts`; the Connect GitHub card mints a token and deep-links GitHub's new-file editor pre-filled) - push-to-deploy without running a build farm; the workflow passes `CLOUDFLAREBASE_GIT_BRANCH`/`_DEFAULT_BRANCH` because checkout's detached HEAD hides the branch name, and webhook builds on our infra stay Phase D. CLI: `link` (interactive claim with dry-run preview), managed `deploy` (branches on `cloudflarebase.json`; wrangler does the bundling via `--dry-run --outdir`), `secret set` (PATCH with `keep_bindings` - sessions only, tokens can't write secrets). Hard v1 caps in the agent (2 apps, 50 deploys/day, 5 MB modules, 1000/25 MB assets); scripts carry a `pid-<projectId>` tag (NOT `project:<id>` - a colon collides with the `?tags=<tag>:yes` filter grammar) that erase bulk-deletes; asset manifest hashes are salted with the project id so tenants can't probe each other's content by hash. **No demo hosting** (403 + upsell card, console and agent both). The self-hosted default has NO `DISPATCH` binding (WfP is paid; deploys 503 honestly); `HOSTING_STUB=true` in local/test records deploys and serves a fixed stub page, honouring `x-cfbase-host` in place of Host. Ports: dev :8790, e2e :8800. Pinned by `e2e/hosting.api.spec.ts` + `e2e/deploy-token.api.spec.ts`; real upload is the opt-in `RUN_HOSTING_E2E=1` spec against the `-preview` namespace.
- **Demo mode.** `DEMO_MODE=true` lets anonymous visitors drive ephemeral `demo-<hex>` projects; named projects still require a session. Demo ids are `demo-<12 hex>` (20 hex before demo branches; both stay valid), and **demos get branches**: the pattern in `$lib/console.ts` AND both agents' `schemas.ts` accepts `demo-<hex>--<branch>` so every family member shares the caps/TTL/anonymous access - keep the three regexes in sync. The branch context is SYNTHESIZED (`demoBranchContext` in `src/lib/server/registry.ts`: the bare root IS `production`, plus `preview` and every branch this visitor minted - no `main`, no registry rows), and creating a demo branch is client-side navigation; server `POST /branches` still refuses demo roots. Custom demo branches are remembered in the `cfbase-demo-branches` cookie (`rememberDemoBranch`, written by the `[projectId]` layout load on visit, one demo family per cookie, 8 names, 24h) - without it a branch the visitor just created vanished from the switcher the moment they navigated to another one, because the id was the only record of it. Bare `/dashboard` branches on the session even in demo mode: the guard resolves it there (no cookie = no lookup), so a signed-in operator gets the real project list and only anonymous visitors get the demo hand-off - an exception scoped to exactly that entry (`demoEntry` in `classifyAccess`), so `/cli-auth` keeps its hard bounce. Unset means a private console, and `/` redirects to the console (the marketing landing page only has an audience on the public demo). Every minted demo id is also logged to the control-plane `demo_project` table - append-only, never pruned - because demo DOs self-erase and auth events age out of Analytics Engine after 90 days; `/admin`'s "Demos created" stat reads this log for the all-time number, after folding fleet-visible demos into it (the log postdates the first demos, so counting it alone would misreport history as zero). In the agent the flag makes demo projects throwaway: capped users, daily inference ceiling, no outbound mail, self-erasure after `DEMO_TTL_HOURS` via `this.schedule(..., { idempotent: true })` so repeated wakes reuse one row. `e2e/demo-project.api.spec.ts` pins that the Integration-tab REST flow works unauthenticated.
- **Control plane vs project state.** Installation-wide state is D1 on the dashboard Worker (`DB`, schema in `src/lib/server/db/schema.ts`); per-project state is that project's DO. The registry is not in an agent on purpose: any agent owning the list makes every other agent depend on it. `database_id` is omitted from deployable configs so deploys provision it; schema is applied at runtime by `src/lib/server/db` - the `project` registry and the `demo_project` log (move to generated migrations when it grows further). Each environment gets its own database - preview binds `cloudflarebase-control-plane-preview`, never production's. Registry rows only make sense relative to the agent binding that wrote them, and runtime schema application means a shared database would let preview code migrate production. Preview ships via `versions upload`, which may not auto-provision, so the preview database is created once by hand: `npx wrangler d1 create cloudflarebase-control-plane-preview`.
- **Deleting a project fans out from the console.** `deleteProject` in `src/lib/server/registry.ts` drops the row, then calls each agent's erase route (`DELETE /internal/projects/:id`, outside `/agents/*`, service-binding-only). A new agent adds a call there, not a dependency between agents. `AuthAgent.destroy()` defers `ctx.abort()` a tick so the response survives.
- **Project branches** (`docs/branches-design.md`, implemented). A branch is a full registry row whose id is `<root>--<branch>` - the derived id IS the isolation, zero agent changes, because every agent keys on project id (own DOs, users, collections, JWKS, replicas). `project` gained `parent_id`/`branch_name` (shipped via the runtime CREATE plus duplicate-column-tolerant ALTERs in `src/lib/server/db/index.ts`); `createBranch`/`listBranches` in `src/lib/server/registry.ts`; routes `POST`+`GET /api/projects/<id>/branches`, operator-only by guard default, and deleting a branch is the ordinary registry DELETE. New root ids refuse `--` (grandfathered rows stay roots - the registry decides what is a branch, never the string shape); branch names are `/^[a-z0-9][a-z0-9-]{0,15}$/` with the combined id under the **48-char** project-id ceiling (mirrored in `src/lib/schemas/auth.ts`, both agents' `schemas.ts`, and the CLI's `schema.ts` - widened from 32 because a long root left room for a 5-character branch, so deployed agents must carry the widening before the console mints an id past 32); no branch-of-branch, no demo branches, and `main` is refused (it would alias the bare id). Deleting a root deletes its branches child-first, each with its own erase fan-out. The per-project OpenAPI document carries `/branches` through `src/lib/openapi/console.ts` - a console-plane module, deliberately not an agent module, because branches are minted by the registry. Dashboard: a `⎇` breadcrumb dropdown plus a sidebar branch select (one shared menu snippet: `main` + branches + a New-branch dialog with a live `<root>--<name>` preview), fed by `getBranchContext` in the `[projectId]` layout load - null hides the controls on unregistered projects, while demo families get the synthesized context described under Demo mode; switching swaps only the URL's project segment so the operator stays on the same tool page, and the projects overview nests branches as indented child rows under their root. Pinned by `e2e/branches.api.spec.ts` + `e2e/branches.ui.spec.ts`.
- **The API reference is generated.** `src/lib/agents.ts` is zod schemas; the `src/lib/openapi/` composer (per-agent modules plus the console-plane `console.ts`) emits an OpenAPI 3.1 document per project (`z.toJSONSchema` emits draft 2020-12) with the project's real base URL, served at `/api/projects/<id>/openapi.json`, rendered by Scalar at `/dashboard/<id>/api`. Every registry schema needs `.meta({ id })`; construction throws at import.
- Realtime state uses `AgentClient` from `agents/client`. Dev connects to :8788 directly; the built Worker proxies `/agents/*` through `src/hooks.server.ts`.
- `AuthAgent` owns CORS and CSRF trust: a deployment trusts its own origin automatically (same-origin is never CSRF; the trustedOrigins function adds the request URL's origin), plus environment `TRUSTED_ORIGINS` and per-project allowed origins for everything else. Exact-origin echo, credentials, exposes `set-auth-token`. Never enable `routeAgentRequest(..., { cors: true })`; its wildcard overrides the project policy. Rate limiting keys on `CF-Connecting-IP` via `advanced.ipAddress.ipAddressHeaders`; without it Better Auth falls back to one shared bucket.
- DO SQLite is authoritative for users and sessions. Auth events go to Analytics Engine; local/test mirror them to D1 for deterministic queries. Reads use the SQL API; dashboard polling and the agent cache are both 5 seconds; daily buckets use the browser's IANA timezone (cache entries are timezone-specific) and the dashboard filters 7/30/90-day windows client-side.
- **Workers AI tool-shape gotcha.** Inference backends disagree about the `tools` array: some accept the flat `{name, description, parameters}` the function-calling docs show, others only the OpenAI wrapper `{type:'function', function:{...}}`, rejecting the flat form with an 8007 "validation errors" body naming `body.tools.N.function`. Which one answers is per-instance, so the copilot appears to work and then fail for the same question. `runInference` in `src/lib/server/copilot.ts` sends one shape, retries the other on a validation rejection, and remembers what worked. Also: the chat route swallows inference errors to keep its 502 contract, so Sentry's `handleError` hook never sees them - it captures explicitly, and adds a `detail` field in dev only.
- **The copilot is a console-orchestrated tool loop.** The web Worker's `/api/projects/<id>/chat` route runs the Workers AI function-calling loop (`src/lib/server/copilot.ts`; binding `AI`, model var `CHAT_MODEL`; env.local uses `"remote": true` since Workers AI has no local simulator, and env.test/wrangler.e2e.jsonc deliberately have no AI binding so e2e chat 502s deterministically). Tools read BOTH agents over the service bindings: auth `/overview` + `/analytics`, db `/overview` + `/admin/query` (max 20 docs, results truncated to ~6k chars). History is control-plane D1 (`chat_message`), keyed per project + client key: the operator's user id, else a project-scoped SHA-256 of the connecting IP - raw IPs are never stored. Demo projects keep the 50-question daily ceiling (429) and get a lazy 30-day purge of their rows. The response contract mirrors the auth agent's old `/chat` exactly (`{ messages }`, `AgentChatReply`, 400/429/502 with the same strings); inference failure persists nothing. The auth agent still ships its `/chat` surface but the console no longer calls it, and old DO transcripts were not migrated. Real AI e2e coverage is opt-in and never faked.
- **The console shell is Neon-style, page-per-tool.** The `[projectId]` header is a breadcrumb - logo (below `lg`; the sidebar wordmark carries the brand on desktop) / project ⇅ dropdown (registry roots, gated on `locals.consoleUser` so demo visitors get a static crumb and never see the registry) / `⎇` branch ⇅ dropdown; root and branch stay separate crumbs (`project-badge` names the ROOT, which the landing demo spec reads). The sidebar has labeled groups - PROJECT (All projects, Overview), BRANCH (a branch select), one FOLDABLE group per agent driven by manifest `console.pages` (each page has its own route and lucide `icon`, fallback the agent icon), Coming soon, Reference - and below `lg` the same aside slides in behind a hamburger. Tool pages are optional-param routes with matchers (`db/[[tool=dbtool]]`: collections default, tables, sql, access, replication, integration; `auth/[[tool=authtool]]`: users default, sessions, roles, settings, playground, integration); old `?tab=` deep links 308-redirect in the server loads, auth hash deep-links forward client-side, and nav highlighting is exact-match. Not every auth page carries the whole shell: charts + analytics side column are Users-only, stats also ride on the playground. **The db tool pages are table-editor-shaped:** Tables (`db/tables-tab.svelte`) is a permanent table rail plus a full-bleed data grid (sticky header, typed column headers with per-type icons, row checkboxes and a bulk bar, hover row actions), the schema designer opens as a right sheet instead of taking half the page, and the row editor is one typed field per declared column with a JSON toggle (`db-row-mode-form|json`) - NULL is never the starting position on insert, or the field would open disabled. Grid rows re-read on every `tables` prop identity change, which is the parent's agent-state push (~500ms after any write, from any client) plus its 5s poll - the same live path the collections browser rides. Collections keep the Firestore Miller columns; the third column is a field list with inferred types (`fieldType`) over an id/owner/created/updated metadata block. Deleting a row or a document is confirmed in an AlertDialog, never a bare click or a native `confirm()`. **Every operator list pages rather than truncating** - the collections browser, the tables grid, and the auth users/sessions tables all render a `range of total` readout plus Prev/Next over the agents' KEYSET cursors (no offset anywhere: rows land mid-scan and an offset would skip or repeat them). Prev walks a client-side stack of the cursors that started each page; the 5s poll re-reads the CURRENT page, so live refresh never yanks an operator back to the top; a page emptied by deletes falls back to the first. The collections browser is height-bounded (`lg:h-[34rem]` **plus `lg:grid-rows-1`** - a fixed-height grid alone does NOT bound its items, because the implicit row track is `auto`/max-content, so the columns stretched past the container and their `overflow-y-auto` never engaged; `grid-rows-1` is `repeat(1,minmax(0,1fr))`, which is what makes the row honour the height) so its three columns scroll internally instead of growing the page - which is also why selecting a document needs no scrolling on desktop, and scrolls the fields column into view only below `lg`. **Live activity is per tool page**, not a tabbed card: `activity-card.svelte` is shared, the collections page passes collection/document events (plus `project.*`) and the tables page passes table/row events.
- Theme state is owned by root `ModeWatcher`; all theme buttons use `$lib/components/mode-toggle.svelte`. Never touch the root `dark` class or storage directly.
- The project agent is a docked, resizable right pane (PaneForge via the shadcn `resizable` wrapper), open by default on desktop, collapsible to a rail. Open state and sizes persist in the `cfbase-copilot` cookie, read by `+layout.server.ts` so SSR renders without a resize flash. Below 1024px (shared `IsMobile` hook; the layout's CSS gates use `lg:` to match) a bottom tab bar swaps in a full-screen agent view. The shell is viewport-height; pages and chat scroll inside `ScrollArea` viewports, not the window. Exception: the API reference page opts out (layout branches on `isApi`) because Scalar pins its sidebar with `position: sticky` against its nearest scroll container; the page's own `overflow-auto` wrapper is the scrollport, mirroring Scalar's embedded layout.
- `/admin` is the fleet dashboard, gated by `ADMIN_SECRET` - optional on purpose: unset (the self-hosted default; no config has required secrets, so a fresh clone deploys with zero configuration), `/admin` reports itself unconfigured and everything else works. Enable it with `wrangler secret put ADMIN_SECRET` (plain var only in local/test); cloudflarebase.com's own `env.production`/`env.preview` declare it required. The cookie stores a SHA-256 digest, so rotating the secret signs admins out. No registry involved: the agent worker's `GET /fleet/overview` lists projects from auth-event analytics, then asks each project DO for counts and colo over RPC (`getFleetCounts`). `/fleet/*` sits outside `/agents/*` so it is service-binding-only.
- Shared DTOs in `src/lib/agents.ts` mirror `agents/auth/src/agent.ts`, `fleet.ts`, `agents/db/src/{agent,schemas}.ts`, and `agents/hosting/src/agent.ts`. Keep the copies synchronized.
- **The db agent is shard-per-DO** (`agents/db/CLAUDE.md`, v1 plan in `docs/db-agent-plan.md`, scale roadmap in `docs/db-scale-plan.md`): `DbAgent` coordinates a project (registry with `kind: collection|table`, state sync, erase fan-out); each collection is its own `DbCollection` Durable Object and each SQL table its own `DbTable` - plain DOs on the raw WebSocket Hibernation API sharing the extracted `LiveShard` live-query engine, deliberately not SDK Agents - holding documents (zod query DSL, SQL compiler + JS matcher from one parsed query) or schema-first typed rows (ORM-compatible storage: physical table named after the declared table, plain `id`/`owner`/`created_at`/`updated_at` system columns, JS-enforced types since SQLite affinity enforces nothing), with per-subscriber live queries whose state lives in SQLite. Registry names are unique across kinds. **Per-shard replication** (`replication: 'off' | 'auto'`, **default auto for every shard, demos included**; `off` is the explicit single-region opt-out; REP1 substrate in `docs/db-replication-design.md`): primaries keep a row-image change log and answer writes with `cfb-lsn` session bookmarks; per-region replica instances (`…:r:<region>:1`, same classes, role by name) bootstrap and pull from the primary's feed, serve region-routed reads with D1-style read-your-writes (`cfb-min-lsn`), and forward anything they cannot serve back to the primary - routing staleness is never a correctness bug. Under subscriber socket pressure a region spawns sibling replicas (`…:r:<region>:2`…, threshold 24k of the ~32k ceiling, cap 8, demo shards excluded); drained siblings linger hibernated. Restores bump a parent-owned epoch that forces replica re-bootstrap; erases destroy replicas first via the primary's durable replica registry. Per-collection ceilings: 10 GB / ~1k req/s / no read replicas (push-based live queries are the mitigation). Access modes `public|auth|owner` verify auth-agent JWTs via JWKS over the `AUTH_AGENT` service binding (or the co-located `AuthAgent` namespace in single-worker consumer installs); with neither, token-gated collections 503 and public ones work. Cross-collection batches/transactions are deliberately unsupported. Post-v1 additions (per shard, tables at full parity since T3): permission keys checked against the JWT `permissions` claim (`*` wildcard; 403, not 401) plus declarative document validators on public writes (operator surfaces bypass both, Firestore-Admin-SDK style; tables enforce their declared schema instead of validators), count/sum/avg aggregates, NDJSON export/import (operator import preserves ids/owners/timestamps), and 30-day point-in-time restore over DO SQLite bookmarks with an undo bookmark - 501 in local dev, which keeps no durable change log; the parent serves all six backup/restore admin actions for both kinds through one adapter, and the dashboard's rollback dialog is shared between the collections browser and the tables workspace. **Realtime is standardized over one socket** (`docs/db-gateway-design.md`, implemented): `GET /agents/db-agent/<pid>/realtime` upgrades on a `DbGateway` DO in the subscriber's region; frames add a `shard: { kind, name }` address, shards register the subscription themselves (re-verifying tokens - the gateway is never trusted) and RPC resolved frames back (`gatewayDeliver` wakes hibernated gateways; never an outgoing socket). The SDK multiplexes all collection and table subscriptions over this one socket by default with a permanent per-shard fallback when the endpoint never answers; gateway siblings spawn under socket pressure via the parent's registry, and `GET /admin/realtime` lists them. The dashboard Access tab renders each collection's config as a live plain-English sentence (including replication, with the per-shard on/off select); the Replication tab is a read-only globe - continent silhouettes with arcs from an abstract primary hub to each live region, stat tiles, and a per-region numbers table fed by `GET /admin/replication/:name` fan-out (statuses are per shard). Generated document ids are UUIDv7 (`v7` from the `uuid` package, in both the agent and the dashboard - a deliberate runtime dep, replacing the hand-written ULIDs), so the default id order is chronological; invariants pinned by `agents/db/src/uuidv7.unit.test.ts`. Primaries also self-report their colo (`agents/db/src/colo.ts`, a cached `/cdn-cgi/trace` probe in `repStatus`; nulls in local dev), which is what places the Replication tab's hub.

## Playwright e2e

`npm test` boots a production-mirroring stack: the built SvelteKit Worker on :8797 (`wrangler.e2e.jsonc`), the auth agent on :8798, the db agent on :8799, and the hosting agent on :8800 (all env `test`), with real workerd, service bindings, DO SQLite, and API seeding.

- The web build sets `E2E_BUILD=true`, sending adapter output to `.svelte-kit-e2e/cloudflare` so a running dev process cannot lock the e2e build on Windows. Keep `wrangler.e2e.jsonc` aligned with root compatibility flags and bindings.
- State lives in `.wrangler/test-state/`, cleared when Playwright starts a server. Local runs reuse servers, so seeds are idempotent and generated identities must be unique; CI never reuses. Rate limiting is disabled only in `env.test`; the fixed test secret belongs only in `env.test.vars`.
- Projects run `console` → `seed` → `api` and `chromium`. `console.setup.ts` claims the owner and saves the session to `e2e/.auth/console.json`, loaded as `storageState` by later projects; without it everything is 401. On reused stacks the second claim 403s by design and the sign-in after it is what matters.
- Specs proving a route is closed opt out with empty `storageState` (`console-guard.api.spec.ts`, `demo-project.api.spec.ts`). Tests that create users target `SCRATCH_PROJECT`, never `SEED_PROJECT`, whose counts are asserted exactly.
- API contexts must send `Origin`. Set `BASE_URL` for a deployed target; local server startup is then skipped, along with the direct-agent smoke test (no public route) and the admin fleet spec (unknown `ADMIN_SECRET`).
- UI tests use `data-testid` contracts. Auth dashboard tests call `gotoAuthPage()`, which waits for `data-hydrated="true"`; clicking an SSR-rendered tab earlier loses the event.
- `RUN_AI_E2E=1` includes real Workers AI inference tests; `RUN_HOSTING_E2E=1` (against a WfP-configured stack) includes the real dispatch-namespace upload spec.

## Gotchas

- DO SQLite blocks `pragma_table_info()` and explicit `BEGIN`/`COMMIT` with `SQLITE_AUTH`. No Better Auth Kysely migrations; Drizzle migrations with `transaction: false`.
- Miniflare service bindings are realm-sensitive: call `binding.fetch(url, init)`, never a Node-realm `Request`, and convert responses with `toNativeResponse` before returning from SvelteKit.
- **WebSocket upgrades can never go through a `+server.ts` proxy.** A 101 carries a `webSocket` and a status `new Response` refuses, so `toNativeResponse` re-wrapping one throws `RangeError` - which is how a client that dialled `/api/projects/<id>/db/collections/<c>/subscribe` (instead of letting the SDK rewrite to `/agents/...`) got a 500. `applicationHandle` forwards any `Upgrade: websocket` request on `/api/projects/<id>/<prefix>/**` straight to the agent binding, untouched, exactly like `/agents/*` and still behind the guard; `toNativeResponse` passes an out-of-range status through instead of throwing. Pinned by the proxy-base subscribe test in `e2e/db-live.api.spec.ts`.
- Run agent Wrangler commands from the agent's own directory - `agents/auth`, `agents/db`, or `agents/hosting` (at the root they target the web Worker). `--env preview` targets the `-preview` worker.
- Deploy order is auth → db → hosting → web (`deploy:all` encodes it): the db worker's `AUTH_AGENT` service binding and the web worker's agent bindings each need their target to exist first. For cloudflarebase.com the hosting agent additionally needs `hosting-outbound` deployed first (its `deploy:production` encodes that) and the `cfbase.dev` zone to exist before `env.production` can claim its wildcard route.
- `BETTER_AUTH_SECRET` is a plain var only in local/test; `wrangler secret put` elsewhere. Analytics writes need no token; SQL reads need `CF_ACCOUNT_ID` + `CF_ANALYTICS_API_TOKEN` (Account Analytics Read).
- Never hand-edit generated `worker-configuration.d.ts`; regenerate, and put optional-secret augmentations in a separate `.d.ts`. Both generated files are lint-ignored.
- `checkJs` stays off in the root tsconfig: `wrangler types` emits `GlobalProps.mainModule` as `typeof import()` of the **built** bundle, so with `checkJs` on any tree that has run a build gets thousands of junk errors from type-checking `.svelte-kit/cloudflare/_worker.js`.
- The agent entrypoint may only export handlers and DO classes. A value export fails at boot with `Incorrect type for map entry`, which reads like a config error. Type-only exports are fine.
- **Sentry only sees errors that ESCAPE.** `handleErrorWithSentry` never fires for SvelteKit's `error(status, ...)` (an `HttpError` is returned to the client without reaching the hook), and the Worker/DO instrumentation only catches throws - so anything caught and turned into an error response, or degraded into an empty/null payload, is invisible. Use `serverError()` from `src/lib/server/agents.ts` instead of `error()` for 5xx, and capture explicitly before returning a degraded result. The agents' worker entrypoints additionally report every response `>= 500` (the db worker's hot path included), wrapped so reporting can never replace the response.
- Sentry DSNs stay empty in the top-level self-hosted defaults - a DSN there would collect every fork's errors, and empty disables reporting. cloudflarebase.com's own `env.production`/`env.preview` blocks carry real DSNs on purpose: those blocks are not deployed by forks, and a DSN is browser-visible by design anyway.
- **Two unrelated rate limits, don't confuse them.** `API_RATE_LIMITER` (a Workers rate-limiting binding, all five `ratelimits` blocks in `wrangler.jsonc`, applied in `apiRateLimitHandle`) is per-IP over `/api/*` — which includes the REST **proxy base**, so it is an application throughput limit, not a console one; it is 1000/10s (100 req/s per IP, up from a 100/60s that was 1.7 req/s and 429'd real apps). The sizing constraint is the SHARD, not the console: a Durable Object is single-threaded at ~1k req/s, so a per-IP allowance near that would let one client saturate a whole project. Cloudflare accepts `period` of **only 10 or 60**, and the counter is per **Cloudflare location**, not global, so one key accumulates independently per colo and this can never be sized as a hard global cap. Keying on IP is an abuse ceiling, not fair-share (a customer's server-side backend is thousands of end users behind one IP) - real per-tenant throughput limiting belongs per project. `/agents/*` bypasses it entirely, which is why the SDK hot path is unaffected. Better Auth's limiter (`agents/auth/src/auth.ts`) is separate, covers `/api/auth/*` only, and stays tight on sign-in/sign-up (10/min) because it is anti-credential-stuffing, not throughput. Neither raises the real ceiling: a Durable Object is single-threaded at ~1k req/s per instance, and you scale past that by sharding, region replicas, and gateway siblings.
- `TRUSTED_ORIGINS` is only for origins other than the deployment's own (the agent trusts its own origin automatically). A cross-origin request from an unlisted origin gets an explicit 403 `INVALID_ORIGIN`, never a credential error.
- On Windows, killing only a listening workerd leaves its Wrangler parent alive with children that lock persistence dirs. `scripts/kill-port.mjs` kills the full tree (match scoped to Wrangler); `scripts/clean-dir.mjs` only accepts `.wrangler/test-state` targets and retries `EBUSY`/`EPERM`.
- Workers Builds is connected to the single web Worker `cloudflarebase-com`: the production branch deploys `--env production`, non-production branches upload preview **versions** with `--env preview`. Every command CI runs must resolve the name `cloudflarebase-com` - a "Failed to match Worker name" warning means the resolved config name and the connected Worker disagree, and never merge the automated rename PR Workers Builds offers. Corollary: `wrangler deploy --env preview` from a machine would live-deploy preview bindings (the preview agent!) onto production - preview goes out only as `wrangler versions upload --env preview`, which is why no npm script wraps it.

## Conventions

- Svelte 5 runes, shadcn-svelte under `$lib/components/ui`, LayerChart, `mode-watcher`, tabs, single quotes.
- Routes are grouped: `(marketing)` holds the landing page and the `(legal)` subgroup (`/privacy`, `/terms` — prose mapped onto shadcn tokens in the subgroup layout); `(app)` holds `login`, `admin`, `dashboard`. The legal pages describe cloudflarebase.com's actual demo-mode behavior (no accounts, no emails collected, analytics fields, retention) — recheck them when data handling changes. `api/` and the root layout/error stay ungrouped (groups do nothing for `+server.ts` routes but would churn their route ids). Groups appear in `resolve()` route ids (`/(app)/dashboard/[projectId]`), never in URLs.
- Dynamic segments are named for what they hold: `[projectId]`, `[userId]`, `[sessionId]`, never `[id]`.
- New primitives follow the agent contract (`docs/agent-contract.md`): separate npm project under `agents/<name>` shipping a `cloudflarebase.agent.json`, DO classes with `routeAgentRequest` entrypoint, root service bindings per environment, one entry in `src/lib/agent-registry.ts` (which drives guard, dispatch, proxies classification, sidebar, fan-out) plus an `src/lib/openapi/<name>.ts` module, proxy routes under `api/projects/[projectId]/<prefix>/`, and one `AGENTS` record entry in `cli/src/lib/agents.ts`.
